PostgREST authorizes each request with a JWT: its `role` claim picks the Postgres role and its other claims are readable in RLS policies. Nuxt PostgREST doesn't sign users in. Use any auth library for that. The module gives you three small server utilities that connect it to PostgREST:

```text
your auth library signs the user in
        ↓
mintJwt()  →  setPostgrestToken()      (server)
        ↓
cookie  →  usePostgrest() / usePostgrestUser()   (every request, including client-side navigation)
```

::note
Step-by-step setups for popular libraries are in the playbooks: [nuxt-auth-utils](/playbooks/auth-nuxt-auth-utils), [Better Auth](/playbooks/auth-better-auth), [Sidebase Nuxt Auth](/playbooks/auth-sidebase) and [Clerk](/playbooks/auth-clerk). This page explains the utilities they use.
::

## Set the JWT secret

`mintJwt()` signs tokens with the same secret PostgREST verifies them with:

```bash [.env]
# Must equal PostgREST's jwt-secret (PGRST_JWT_SECRET)
NUXT_POSTGREST_JWT_SECRET=replace-with-a-secret-of-at-least-32-characters
```

::warning
Anyone with this secret can mint a token for any role, including one that bypasses RLS. It is server-only and must never be a `NUXT_PUBLIC_*` variable.
::

## `mintJwt(claims, options?)`

Signs a JWT (HS256) and returns it. Server routes only. Auto-imported in `server/`.

```ts
const token = await mintJwt({ role: 'authenticated', sub: user.id }, { expiresIn: '1h' })
```

| Argument | Type | Description |
| --- | --- | --- |
| `claims.role` | `string` | Postgres role PostgREST switches to, such as `authenticated`. Required. |
| `claims.*` | `unknown` | Any other claims, such as `sub`. Readable in RLS policies, see [below](#reading-claims-in-rls-policies). |
| `options.expiresIn` | `string \| number` | Lifetime: a duration like `'15m'`, `'1h'` or `'7d'`, or seconds. Default `'1h'`. |
| `options.expiresAt` | `Date \| number` | Absolute expiry, as a `Date` or milliseconds since the epoch, for example your session's `expiresAt`. Wins over `expiresIn`. |

## Reading claims in RLS policies

PostgREST exposes the token's claims to Postgres as the `request.jwt.claims` setting, so a policy can compare a column to the signed-in user:

```sql
create policy "owners read their todos" on public.todos
  for select to authenticated
  using (owner = current_setting('request.jwt.claims', true)::json ->> 'sub');
```

The `true` makes it return `null` instead of raising an error when there is no token, so the same policy is safe for anonymous requests.

## `setPostgrestToken(event, token)`

Stores the token in the `nuxt_postgrest_token` cookie, which `usePostgrest()` and `usePostgrestUser()` read. Auto-imported in `server/`.

- It lasts as long as the token's `exp`, and it's `SameSite=Lax`.
- It's `Secure` whenever the request came in over HTTPS, including behind a proxy that sets `X-Forwarded-Proto`.
- It is **not** `HttpOnly`, so the browser can read it. See [why](#why-the-cookie-is-readable-by-javascript) below.

Storing an already expired token throws.

## `clearPostgrestToken(event)`

Removes the cookie, for example on logout. Requests then fall back to the anon key. Auto-imported in `server/`.

::note
The `event` these utilities take is whatever your route handler receives: an `H3Event` on Nuxt 4, a `RequestEvent` (from `nuxt/server`) on Nuxt 5. Both are accepted.
::

## What happens on each request

`usePostgrest()` and `usePostgrestUser()` resolve the token in this order:

1. The `token` option, if you pass one
2. The token cookie
3. The public anon `key`
4. No `Authorization` header (PostgREST's `db-anon-role`)

`usePostgrest()` works during SSR and in the browser. In the browser it reads the cookie on every request, so a client created once, in a store or plugin for example, picks up logging in, logging out and expiry without being recreated.

## Expiry

An expired cookie is ignored, and requests fall back to the anon key instead of failing with `PGRST301`. The module doesn't refresh tokens, so decide how long a token should live:

- **Match your auth session.** Mint with `expiresAt` set to the session's expiry, so the token and the session end together. This is the simplest model.
- **Sliding sessions.** If your library extends the session while the user is active, a token minted at sign-in keeps its original expiry. The user stays signed in, but queries quietly run as anon. Re-mint on each request instead, as the playbooks for Better Auth, Sidebase and Clerk do.
- **A JWT can't be revoked.** Your auth library can end a session immediately, but PostgREST only checks the signature. Banning a user or signing them out elsewhere doesn't stop an already issued token until its `exp`. If that window matters, use shorter sessions.

## Why the cookie is readable by JavaScript

Queries made in the browser after client-side navigation need the token, so the cookie can't be `HttpOnly`. That means a script running on your page, through an XSS bug for instance, can read it. To limit the damage:

- Keep tokens short-lived.
- Give the role only the access RLS should allow.
- Set a strict Content Security Policy.

## Passing a token yourself

The `token` option overrides the cookie, for example to act as a different user for one request:

```ts
const client = usePostgrest({ token })
```

```ts [server/api/todos.get.ts]
export default defineEventHandler(async (event) => {
  const client = usePostgrestUser(event, { token })
  // ...
})
```

## Anonymous requests

With no valid cookie, the client falls back to the public `key`, and with no key it sends no `Authorization` header at all. PostgREST then runs the query as its `db-anon-role`.
